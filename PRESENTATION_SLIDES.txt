SLIDE 2 — PROBLEM & CONTEXT
================================================================================

PROBLEM STATEMENT (GENERIC)
----------------------------
In any large-scale software organisation, change is constant — and change is
the leading cause of failure. Every day, hundreds of engineers across hundreds
of teams push updates to production systems: version upgrades, configuration
adjustments, database schema migrations, API contract changes, and dependency
bumps. Each change looks small in isolation. But in a modern microservices
architecture, nothing is truly isolated.

The fundamental problem is a knowledge gap at the moment of action.

  - The engineer who wrote the runbook three months ago is no longer on-call.
  - The postmortem that documented last quarter's outage lives in a Confluence
    page nobody opens at deploy time.
  - The dependency graph that shows which downstream services call this API
    exists — but it is buried in an architecture diagram updated six months ago.
  - The compatibility matrix for "Spring Boot 3 requires Java 17" is tribal
    knowledge, not a gate.

By the time an engineer clicks "Deploy", they are making a risk decision based
on incomplete information, under time pressure, without access to the
institutional memory of every similar change that has ever been attempted.

The gap between "what we know collectively as an organisation" and "what the
engineer knows right now" is where production incidents are born.

REAL-WORLD PROBLEM: WHERE THIS HAPPENS TODAY
---------------------------------------------
This is not a hypothetical. It is a documented, recurring failure pattern
across the industry:

  REAL INCIDENT 1 — Amazon (2013)
  A configuration change to a subsystem managing connections caused a
  cascading failure that took down major AWS services for several hours.
  Root cause: the impact of a single configuration change on downstream
  dependencies was not fully understood before deployment.

  REAL INCIDENT 2 — Facebook / Meta (2021)
  A routine BGP configuration update caused a global 6-hour outage affecting
  3.5 billion users. The engineer deploying the change had no automated system
  to predict that this specific change would sever DNS routing for all services.
  Loss estimate: ~$60 million in revenue + significant reputational damage.

  REAL INCIDENT 3 — Knight Capital Group (2012)
  A software deployment activated a dormant trading algorithm due to a missed
  configuration flag. The firm lost $440 million in 45 minutes.
  Root cause: no pre-deployment risk system flagged that a flag change would
  have fundamentally different behaviour in production vs. staging.

  REAL INCIDENT 4 — Cloudflare (2019)
  A regex change in a WAF rule caused 100% CPU utilisation across all machines
  globally, taking Cloudflare offline for 27 minutes. The change looked safe
  in isolation but was not tested against production traffic patterns.

  REAL INCIDENT 5 — Salesforce (2022)
  A database script deployed to production accidentally granted read/write
  access to all customer data for a window of time. A pre-deployment schema
  change analysis would have flagged the permission scope anomaly.

THE COMMON THREAD ACROSS ALL THESE INCIDENTS
---------------------------------------------
  "Someone made a change. Nobody had a system that said: this specific change,
   in this specific context, given this specific history, carries THIS level
   of risk — and here is exactly why."

WHAT IS MISSING IN THE INDUSTRY TODAY
--------------------------------------
  - CI/CD pipelines check: Does the code compile? Do tests pass?
  - They do NOT check: Will this change cause a cascade? Has a similar change
    failed before? Does this change violate a known compatibility rule?
  - Change Advisory Boards (CABs) are manual, slow, and not scalable to
    hundreds of daily deployments
  - Existing APM tools (Datadog, New Relic) detect failures AFTER they happen
  - There is no widely adopted system for PRE-deployment risk intelligence

TARGET USERS / STAKEHOLDERS
----------------------------
- DevOps / Platform Engineers    : Need a fast, automated pre-deployment gate
- Site Reliability Engineers     : Need explainable risk scores, not black boxes
- Engineering Managers           : Need rollout recommendations they can defend
- On-Call Teams                  : Need historical context surfaced automatically
- CTO / VP Engineering           : Need to reduce MTTR and deployment-related P1s
- Compliance / Security Teams    : Need auditable change risk records

WHY THIS PROBLEM MATTERS (BUSINESS & OPERATIONAL RELEVANCE)
------------------------------------------------------------
- Industry average: 22% of production outages are caused by failed deployments
  (DORA State of DevOps Report 2023)
- Mean Time to Recover (MTTR) from a deployment-caused incident: 2–4 hours
- For a critical service (payments, checkout), 1 hour of downtime =
  $100K–$500K in direct revenue loss for a mid-size e-commerce platform
- Engineering teams spend 30–40% of incident response time just understanding
  "what changed and what it affected" — time that pre-deployment intelligence
  could eliminate entirely
- Most teams have runbooks, post-mortems, and incident docs — but they sit in
  Confluence, Jira, and Slack, never consulted at deploy time
- ChangeGuardian AI closes this gap by surfacing institutional knowledge at the
  exact moment it is most needed: before the change goes live

SLIDE 3 — SOLUTION OVERVIEW

SOLUTION ARCHITECTURE / WORKFLOW
---------------------------------
  Natural Language Change Request
             |
             v
  [1] Intake Agent
      - Extracts: service name, old value, new value, extra params
      - Uses regex + keyword matching
             |
             v
  [2] Scenario Router Agent
      - Classifies into 1 of 6 change types:
        framework_upgrade | resource_change | db_schema |
        api_contract | shared_dependency | event_schema
             |
             v
  [3] Graph Impact Agent  (Graph RAG — NetworkX)
      - Builds a directed dependency graph of all microservices, databases,
        APIs, Kafka events, and shared libraries
      - Traverses upstream + downstream to find ALL affected services
      - Edge types: CALLS, USES_DB, DEPENDS_ON, CONSUMES_API,
                    PRODUCES_EVENT, CONSUMES_EVENT
             |
             v
  [4] Hybrid RAG Agent
      |-- Vector RAG (FAISS + all-MiniLM-L6-v2):
      |   Embeds historical incident documents and retrieves the most
      |   semantically similar past incidents to the current change
      |
      |-- Vectorless RAG (pure Python rule engine):
          Exact constraint checks — Java version compatibility,
          memory safety buffer, NOT NULL backfill, API field rename
          detection, library breaking version, Kafka field consumers
             |
             v
  [5] Memory Graph Agent
      - Checks a deployment history store for prior rollouts on the
        same service or with a similar change pattern
      - Surfaces past failures and their lessons
             |
             v
  [6] Risk & Rollout Agent  (fully deterministic, no LLM)
      - Calculates a 0-100 risk score from weighted rules:
        criticality + affected services + incidents + violations + memory
      - Maps score to Low / Medium / High / Critical
      - Recommends: Direct | Canary | Staged-Rollout | Block
             |
             v
  [7] LLM Explanation Agent  (AMD Local LLM via Ollama)
      - Sends full risk analysis to Qwen2.5 running on AMD hardware
      - Returns: 3-sentence plain-English explanation + 3 remediation steps
             |
             v
  Final Risk Report (printed + Gradio UI)

AI APPROACH USED
----------------
- Multi-Agent Orchestration   : LangGraph stateful 7-node pipeline
- Hybrid RAG                  : Graph RAG + Vector RAG + Vectorless RAG combined
- Graph RAG                   : NetworkX dependency graph traversal
- Vector RAG                  : FAISS cosine similarity on incident embeddings
- Vectorless RAG              : Deterministic Python rule engine (zero hallucination)
- Memory Graph                : Deployment history store with keyword + exact matching
- Local LLM (GenAI)           : Qwen2.5 running on AMD via Ollama for explanation

KEY TECHNOLOGIES / FRAMEWORKS
------------------------------
  Framework        Version    Role
  ---------------- ---------- ------------------------------------------
  LangGraph        0.2.x      Multi-agent stateful workflow orchestration
  NetworkX         3.x        Dependency graph (Graph RAG)
  FAISS            1.7.x      Vector similarity index (Vector RAG)
  SentenceTransformers 3.x    all-MiniLM-L6-v2 embeddings (384-dim)
  Ollama           0.3.x      Local LLM server (AMD ROCm / CPU)
  Qwen2.5:3b       3B params  Explanation + remediation generation
  Gradio           4.x        Interactive web UI
  psutil           5.x        AMD RAM / CPU monitoring
  Python           3.9        Runtime

WHAT WAS BUILT DURING THE HACKATHON

SLIDE 5 — IMPACT & DEMO SUMMARY
================================================================================

EXPECTED IMPACT / VALUE
------------------------
Efficiency      : Reduces pre-deployment risk assessment from 30–60 minutes
                  of manual review to under 10 seconds automated analysis

Productivity    : Engineers no longer need to manually cross-reference
                  runbooks, incident reports, and dependency maps — all
                  institutional knowledge is surfaced automatically

Scale           : One system handles 6 different change scenarios covering
                  the full spectrum of production risk: framework upgrades,
                  resource changes, database migrations, API contracts,
                  shared dependencies, and event schema changes

Experience      : Risk reports include plain-English LLM explanations and
                  step-by-step remediation — junior engineers can act on
                  them without escalating to senior SREs

Reliability     : Deterministic scoring (every risk point is justified and
                  traceable) eliminates the "black box" problem of pure LLM
                  risk assessment. Judges and operators can audit every score.

Data Privacy    : Runs 100% on-premise on AMD hardware. Change requests,
                  incident history, and service topology never leave the
                  network. Critical for financial services, healthcare, defense.

KEY DIFFERENTIATORS / INNOVATION
----------------------------------
1. HYBRID RAG FUSION
   Most RAG systems use only vector search. ChangeGuardian AI combines three
   retrieval strategies in one pipeline: Graph RAG (structural dependencies),
   Vector RAG (semantic similarity), and Vectorless RAG (exact rule matching).
   Each retrieves information no other method can.

2. DETERMINISTIC + LLM HYBRID SCORING
   The risk score (0-100) is calculated by deterministic rules with full
   explainability — no LLM involved in scoring. The LLM is used ONLY for
   natural language explanation and remediation suggestions. This means
   the system is auditable, reproducible, and trustworthy.

3. AMD-NATIVE ON-PREMISE EXECUTION
   The entire system — embeddings, graph traversal, rule engine, LLM inference
   — runs on AMD hardware with no external API dependency. This is a
   production-deployable architecture for enterprises that cannot send
   deployment metadata to cloud APIs.

4. MEMORY GRAPH LEARNING
   The system incorporates a deployment memory store that surfaces lessons
   from prior rollouts. If payment-service failed a Spring Boot upgrade before,
   that lesson is retrieved and factored into the risk score automatically.

5. SCENARIO COVERAGE
   Six distinct production change scenarios are handled by a single unified
   pipeline — not six separate tools. The Scenario Router agent classifies
   the natural language request and the correct risk rules activate.
